GameHub on Google Cloud Platform - what was deployed, why, and what to do
as usage changes. Written 2026-07-23.

This is a SEPARATE deployment from the one described in "deployment
guide.txt" (the Windows laptop + home router + Caddy + self-managed
Postgres setup). Both can run at the same time - they use different
databases and don't know about each other. This document assumes you've
read "deployment guide.txt" section 3 (what moving to cloud would take) -
this is that plan, actually carried out.

---------------------------------------------------------------
1a. Why db-f1-micro, and why Cloud SQL for Postgres can't go smaller
---------------------------------------------------------------

Cloud SQL for MySQL offers even smaller shared-core tiers than Postgres
does. For Postgres, db-f1-micro (614 MiB RAM) is the actual floor - there
is no smaller option, and the "Enterprise Plus" edition (Cloud SQL's
default if you don't specify --edition) doesn't offer shared-core tiers
at all, only the larger "perf-optimized" machine types. Creating this
instance required explicitly passing --edition=ENTERPRISE to unlock
db-f1-micro - the first creation attempt failed with exactly this error,
which is how this was discovered rather than assumed.

At 5-10 concurrent users this is plenty - Postgres for a text/JSON API
like this one is nowhere near CPU or memory-bound at that scale. The
thing db-f1-micro genuinely limits is peak connection count and query
concurrency under a real spike, not steady-state usage - see section 6
for what upgrading looks like when/if that becomes the bottleneck.

---------------------------------------------------------------
1b. Why backups are off - a real tradeoff, not an oversight
---------------------------------------------------------------

Automated backups on Cloud SQL cost extra (backup storage is billed
separately from the instance itself) and were left off specifically to
keep the "may stay at $0 traffic forever" case as cheap as possible, per
what you described. The real consequence: if this Cloud SQL instance is
ever deleted, corrupted, or has a bad migration run against it, there is
NO way to recover - no point-in-time restore, no daily snapshot.

This is an acceptable risk at zero-to-low real usage (a handful of test
accounts, nothing anyone would be upset to lose) but stops being
acceptable the moment real users' accounts/stats start accumulating.
Turn backups on with:

    gcloud sql instances patch gamehub-db --backup-start-time=03:00 --project=gamehub-alaab

That's a one-line, fully reversible change (--no-backup to turn back
off) - do this before real users sign up, not after.


====================================================================
2. THE HARD LIMITS THAT ARE SET, AND HOW TO CHANGE OR REMOVE THEM
====================================================================

Three limits are in place. Two are architectural (protect correctness),
one is financial (protects your wallet). None of them are permanent -
all three are single-command changes.

---------------------------------------------------------------
2a. Cloud Run max-instances=1 (architectural, NOT about cost)
---------------------------------------------------------------

This is the most important setting in this deployment and the one most
likely to cause confusing bugs if changed carelessly. Each of the four
multiplayer games (game.py, connect4.py, ludo.py, court_piece.py) keeps
its live board state and WebSocket connections in an in-memory Python
dict, inside whichever single process is running. This was already true
and already documented as a constraint on the laptop deployment (see
"deployment guide.txt" section 3d) - Cloud Run's autoscaling just makes
it possible to accidentally violate that constraint in a way a single
laptop process never could.

If max-instances is raised above 1 without also doing the work
described in "deployment guide.txt" section 3d (moving shared game
state to something external like Redis, and making a given game's
traffic sticky to one instance), here is exactly what breaks: two
players in the same match can get routed by Cloud Run's load balancer to
DIFFERENT container instances. Each instance has its own copy of the
`games` dict. Player A's move updates instance 1's copy; player B, on
instance 2, never sees it. The match silently desyncs - no error, no
crash, just a game that stops making sense. This is exactly why
max-instances stays at 1 until that refactor happens.

(Court Piece was originally a client-only mock with no backend at all,
which genuinely was unaffected by this - that changed on 2026-07-23 when
it was rebuilt with a real backend module for real multiplayer, matching
the other three games exactly, including this same constraint. See
"Redeploying Court Piece's backend" further down for that specific
change.)

To raise it (only after the Redis refactor, or if you're consciously
accepting the desync risk for a quick test):

    gcloud run services update gamehub --region=us-east1 --max-instances=N --project=gamehub-alaab

To confirm the current value:

    gcloud run services describe gamehub --region=us-east1 --project=gamehub-alaab --format="value(spec.template.metadata.annotations)"

Look for `autoscaling.knative.dev/maxScale`.

---------------------------------------------------------------
2b. Cloud Run min-instances=0 (cost, not a hard cap - just scale-to-zero)
---------------------------------------------------------------

This isn't a limit in the "you get cut off" sense - it's what makes the
"$0 traffic forever" case actually cost close to $0 on the Cloud Run side
specifically (Cloud SQL still bills regardless - see section 6). With
min-instances=0, Cloud Run shuts the container down entirely when there's
no traffic, and the first request after a quiet period pays a cold-start
delay (typically 1-3 seconds for this app - installing Caddy at build
time rather than at startup keeps this from being worse). If that
cold-start delay ever becomes annoying at real usage levels, set
min-instances=1 to keep one instance always warm - this has a real,
constant cost (see section 6), it's a tradeoff, not a fix with no
downside.

    gcloud run services update gamehub --region=us-east1 --min-instances=1 --project=gamehub-alaab

---------------------------------------------------------------
2c. Billing budget: $25/month, alerts only (no auto-shutoff)
---------------------------------------------------------------

Created via:

    gcloud billing budgets create --billing-account=0172BF-F4E332-1027B3 \
      --display-name="GameHub monthly budget" --budget-amount=25USD \
      --filter-projects=projects/gamehub-alaab \
      --threshold-rule=percent=0.5 --threshold-rule=percent=0.9 \
      --threshold-rule=percent=1.0 --threshold-rule=percent=1.5

This emails the billing account's admins (tictactoe2300@gmail.com) when
actual spend crosses 50%, 90%, 100%, and 150% of $25/month. It does NOT
stop anything from running and does NOT cap what you can spend - GCP
budgets are alerts, not caps, by design. You will keep getting charged
past $25 if usage keeps climbing; you just won't be surprised by it,
since you'll have gotten three emails first.

A TRUE hard cap (automatically disabling billing on the project when a
threshold is hit) is possible but was deliberately NOT set up, because
of what it actually does: disabling billing makes EVERY billable
resource in the project stop working immediately, not just whichever
one caused the overage. Cloud Run would stop serving, Cloud SQL would
become unreachable, all in one shot, with no warning beyond whatever
alert delay Pub/Sub + Cloud Functions introduces. For an app you might
want to keep working while you investigate a cost spike, alerts you can
react to are almost always the better default than an automatic kill
switch. If you still want the hard-cutoff version later, the standard
pattern is: a budget with Pub/Sub notifications enabled, subscribed to
by a small Cloud Function that calls the Cloud Billing API to disable
billing on the project - Google's own tutorial is at
cloud.google.com/billing/docs/how-to/notify (search that if you want to
set this up; it's a real project's worth of setup, not a single command).

To change the budget amount:

    gcloud billing budgets list --billing-account=0172BF-F4E332-1027B3
      (find the budget's full resource name, looks like
       billingAccounts/0172BF-F4E332-1027B3/budgets/<id>)
    gcloud billing budgets update <full-resource-name> --budget-amount=NEW_AMOUNTUSD

To remove it entirely:

    gcloud billing budgets delete <full-resource-name>

To see current spend without waiting for an alert email, the Cloud
Console's Billing > Reports page is more useful than any gcloud command
for this specific task - there's no clean CLI equivalent for "show me
a cost breakdown by service over time."


====================================================================
3. WHY ONE CONTAINER, NOT TWO CLOUD RUN SERVICES
====================================================================

The laptop deployment runs uvicorn and Caddy as two separate OS
processes, talking over localhost. Cloud Run runs one container per
service and doesn't give you "two processes on the same host" the way a
laptop does by default - the natural cloud-native shape would be two
separate Cloud Run services (one for the API, one serving static files)
behind a load balancer that path-routes between them, similar in spirit
to what Caddy does today.

That's a legitimate design and is the RIGHT eventual move if the
frontend is ever split off entirely (see "deployment guide.txt" section
3i - already documented as optional, not required). For a first cloud
deployment, it adds a load balancer (a real added cost - GCP's HTTP(S)
Load Balancer has its own monthly charge, is not scale-to-zero, and is
a service unto itself) and unnecessary architectural distance from the
laptop's proven Caddy-routes-everything design, right when the goal is
"validate this works in the cloud."

So instead: the Dockerfile installs Caddy INSIDE the same container as
Python/uvicorn, and infra/docker-entrypoint.sh starts uvicorn in the
background (bound to 127.0.0.1:8000, never exposed) then runs Caddy in
the foreground listening on Cloud Run's $PORT - functionally identical
routing to infra/Caddyfile (same handle blocks for /api/*, /ws,
/ws/connect4, /ws/ludo), just adapted in infra/Caddyfile.cloud to listen
on {$PORT} instead of :80/:443/:8080, and with `auto_https off` since
Cloud Run terminates TLS itself before traffic ever reaches the
container - Caddy doesn't need to (and shouldn't try to) get its own
certificate here.

New files this created, none of which touch the laptop deployment path:

    Dockerfile                    (repo root)
    .dockerignore                 (repo root - keeps backend/.env,
                                    backend/pgdata/, and other local-only
                                    files out of the built image)
    infra/Caddyfile.cloud         (Cloud Run-specific Caddy config)
    infra/docker-entrypoint.sh    (starts uvicorn + Caddy together)

infra/Caddyfile (no ".cloud") is untouched and still exactly what the
laptop uses.

3a. THE COLD-START RACE THAT CAUSED INTERMITTENT 502s (fixed 2026-07-23)

Because Caddy and uvicorn are two processes in one container, and
docker-entrypoint.sh originally started uvicorn in the background and
then immediately exec'd Caddy in the foreground, there was a window on
every cold start where Caddy had already opened $PORT (so Cloud Run's
startup probe passed and it started routing real traffic to the
instance) while uvicorn was still importing modules and opening its DB
pool - which took ~40-60 seconds. Any request landing in that window
got proxied to a uvicorn that wasn't listening yet, and Caddy returned
502. This wasn't specific to any one endpoint; it happened to hit
/api/court-piece/stats and /api/auth/me during testing simply because
those were the first requests sent after a fresh deploy/cold start.

Fixed by making docker-entrypoint.sh block on a readiness check
(curling uvicorn's own /api/auth/me in a loop) before starting Caddy,
so Cloud Run's startup probe - which only checks that Caddy's port is
open - now accurately reflects that the whole stack, not just Caddy,
is ready. This costs a bit of extra cold-start latency (the ~40-60s
uvicorn init now happens before the instance is marked ready, instead
of overlapping with early traffic) but trades that for correctness -
scale-to-zero (min-instances=0, see section 2) means this cold start
happens on essentially every first request after idle, so this bug
would otherwise recur constantly for real users, not just during
testing.

4. SECRETS: HOW THEY WERE CREATED, AND HOW TO ROTATE THEM
====================================================================

Three secrets live in Secret Manager, one version each so far:

    PGPASSWORD          - the tictactoe_app Postgres user's password
    SESSION_SECRET       - signs session cookies (itsdangerous)
    GMAIL_APP_PASSWORD    - same Gmail App Password the laptop uses

They were created without ever printing the raw values to a terminal
that logs history (piped from a file straight into `gcloud secrets
create --data-file=`, files deleted immediately after). The Cloud Run
service account (886418271510-compute@developer.gserviceaccount.com,
the default Compute Engine service account - Cloud Run used it since no
custom service account was specified) was explicitly granted
roles/secretmanager.secretAccessor on each of the three secrets
individually - this does NOT happen automatically and the first deploy
attempt failed with a clear permission-denied error until this was done.

To rotate any of them (create a new version, which the running service
picks up on its NEXT deploy/restart - Cloud Run does not hot-reload
secrets into an already-running container):

    echo -n "new-value-here" > /tmp/newval.txt
    gcloud secrets versions add SESSION_SECRET --data-file=/tmp/newval.txt --project=gamehub-alaab
    rm /tmp/newval.txt
    gcloud run services update gamehub --region=us-east1 --project=gamehub-alaab
      (a no-op update forces a new revision, which reads :latest again)

Rotating PGPASSWORD requires changing it in TWO places consistently -
the Cloud SQL user's actual password, and the secret:

    NEWPW=$(python -c "import secrets; print(secrets.token_urlsafe(24), end='')")
    gcloud sql users set-password tictactoe_app --instance=gamehub-db --password="$NEWPW" --project=gamehub-alaab
    echo -n "$NEWPW" > /tmp/pw.txt
    gcloud secrets versions add PGPASSWORD --data-file=/tmp/pw.txt --project=gamehub-alaab
    rm /tmp/pw.txt

(This exact sequence is worth using verbatim - during initial setup,
creating the secret from a Python-generated file via `print()`'s default
trailing newline, while separately deriving the Cloud SQL password via
shell command substitution (which strips trailing newlines), produced
two DIFFERENT values from the "same" password and a confusing
authentication failure. Using `print(..., end='')` and setting both from
the identical in-memory value avoids that class of bug entirely.)

GMAIL_APP_PASSWORD rotation means generating a new Gmail App Password at
myaccount.google.com/apppasswords for tictactoe2300@gmail.com, then the
same `gcloud secrets versions add` pattern as SESSION_SECRET above.

5. HOW TO REDEPLOY AFTER A CODE CHANGE
====================================================================

Two steps - rebuild the image, then point Cloud Run at the new one
(gcloud run deploy with the same image tag does both in one command if
you rebuild first):

    cd C:\Users\thaque2050\Desktop\tic-tac-toe
    gcloud builds submit --tag us-east1-docker.pkg.dev/gamehub-alaab/gamehub/app:latest --project=gamehub-alaab
    gcloud run deploy gamehub --image=us-east1-docker.pkg.dev/gamehub-alaab/gamehub/app:latest --region=us-east1 --project=gamehub-alaab

`gcloud builds submit` uses Cloud Build (no local Docker installation
needed) and takes under a minute for this app's size. The second command
reuses the existing service's configuration (min/max instances, secrets,
Cloud SQL connection, env vars) - you don't need to repeat all the
--set-env-vars/--set-secrets flags from the original deploy unless
you're actually changing one of those values.

If a code change adds a new migration file (007_something.sql,
following the existing numbering), run it against Cloud SQL through the
Cloud SQL Auth Proxy, same pattern used to set this instance up
initially:

    gcloud components install cloud-sql-proxy   (one-time, if not already installed)
    cloud-sql-proxy gamehub-alaab:us-east1:gamehub-db --port 5434 &
    PGPASSWORD=$(gcloud secrets versions access latest --secret=PGPASSWORD --project=gamehub-alaab) \
      psql -h 127.0.0.1 -p 5434 -U tictactoe_app -d tictactoe -f backend/migrations/007_something.sql

Note this needs Application Default Credentials set up specifically
(`gcloud auth application-default login`), which is a SEPARATE
credential store from regular `gcloud auth login` - both were needed
during initial setup, and the Cloud SQL Auth Proxy specifically only
reads the "application default" one. If the proxy logs
`auth: "invalid_grant"` when you try this, that's what's stale - rerun
`gcloud auth application-default login`.

6. WHAT THIS ACTUALLY COSTS - AND WHAT TO WATCH
====================================================================

Reliable, current pricing needs GCP's own pricing calculator
(cloud.google.com/products/calculator) or the Cloud Billing Reports page
once real usage exists - quoting exact per-second rates here would go
stale and potentially mislead a future reader more than it would help,
so this section describes cost SHAPE and what drives it, not a promised
dollar figure.

Cost has two very different characters depending on the piece:

  Cloud Run (compute) - scales with actual usage, close to $0 at $0
  traffic. With min-instances=0, you are billed only for the CPU/memory-
  seconds actually spent handling a request while someone is connected,
  plus request count - both have meaningful free-tier monthly
  allowances. At "may stay at 0 forever," this side of the bill should
  be genuinely near-zero most months.

  Cloud SQL (database) - a small but CONSTANT cost regardless of
  traffic, because unlike Cloud Run, a Cloud SQL instance doesn't scale
  to zero - db-f1-micro bills by the hour whether anyone's playing or
  not. This is the dominant, non-negotiable-at-this-architecture line
  item of the whole deployment, and the main reason the $25/month budget
  in section 2c isn't set lower - db-f1-micro plus 10GB storage alone
  will consume a meaningful chunk of that budget even at zero traffic.
  If you want a database that ALSO scales to zero (relevant given "may
  remain 0 forever" is a real possibility you described), a third-party
  serverless Postgres like Neon is the better fit architecturally - this
  deployment used Cloud SQL because that's what you asked for, but
  switching later is a connection-string change only (config.py already
  just reads PGHOST/PGPORT/etc from the environment - see section 5's
  redeploy process, same idea, different env var values).

Artifact Registry (container image storage) and Secret Manager both
have negligible cost at this scale - a handful of container image
layers and three small secret values, nowhere near their respective
free tiers' limits.

What actually watching costs looks like in practice: check the budget
alert emails (section 2c) rather than trying to predict a number in
advance - they'll tell you within a day or two of crossing 50%/90%/100%/
150% of $25, which is a far more reliable signal than any estimate
written here months before real usage exists.

7. WHAT TO DO IF USAGE ACTUALLY GROWS
====================================================================

Roughly in the order you'd hit them, going from "maybe 0 forever" to
real traffic:

7a. Cold starts become noticeable/annoying
   - Set min-instances=1 (section 2b). Real, constant cost from that
     point on, in exchange for no first-request delay.

7b. You want alaab.ai (or a GCP-specific subdomain) instead of the
    run.app URL
   - Cloud Run supports custom domain mapping directly:
     `gcloud run domain-mappings create --service=gamehub --domain=YOUR_DOMAIN --region=us-east1`
     then point a DNS CNAME/A record at what that command outputs.
     This is a separate, additional DNS record from whatever the laptop
     deployment already uses for alaab.ai - decide whether this Cloud
     Run deployment is meant to REPLACE the laptop one (in which case
     you'd eventually repoint alaab.ai's existing DNS record here and
     retire the laptop + DDNS task) or run alongside it under a
     different hostname. Nothing here does that automatically - both
     deployments are independent today.

7c. You need more than 1 Cloud Run instance (~dozens of concurrent
    users sharing one process starts to strain a single instance's
    CPU/memory, or you want zero-downtime deploys)
   - This is the point where "deployment guide.txt" section 3d's shared-
     state requirement stops being theoretical. Before raising
     max-instances past 1 (section 2a), move the `games` dicts in
     game.py/connect4.py/ludo.py to something external (Redis is the
     standard choice - Cloud Memorystore for Redis is GCP's managed
     option) and ensure a given match's WebSocket traffic stays sticky
     to one instance, or route game-state reads/writes through the
     shared store instead of in-process memory. Skipping this and just
     raising max-instances will cause the silent desync failure mode
     described in section 2a.

7d. Cloud SQL db-f1-micro becomes a bottleneck (slow queries under
    real concurrent load, connection limit errors)
   - Resize with `gcloud sql instances patch gamehub-db --tier=db-g1-small` (or larger) -
     this causes a brief restart (seconds to low minutes), not a
     migration - same instance, same data, same connection details,
     just more CPU/RAM behind it. No application code or config changes
     needed.

7e. Real user accounts exist and matter
   - Turn Cloud SQL backups on (section 1b) - do this before 7e becomes
     true, not after.
   - Rotate SESSION_SECRET, PGPASSWORD, and GMAIL_APP_PASSWORD (section
     4) if you have any doubt they've been handled carefully up to this
     point - cheap insurance once real accounts are on the line.

7f. Thousands of users, sustained traffic
   - This is genuinely a different capacity planning conversation than
     what fits in a "how to change a setting" document - revisit
     Cloud SQL's tier again (7d), consider whether min-instances should
     be higher than 1, and whether the frontend should split off to a
     CDN (Cloud Storage + Cloud CDN, or any static host - "deployment
     guide.txt" section 3i already covers what that requires
     code-side: CORS + a cookie SameSite change). None of this is
     needed to go from 0 to a few hundred users; it's here so this
     document doesn't imply the ceiling is lower than it actually is.
